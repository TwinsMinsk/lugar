## Purpose

The migration history for the PostgreSQL schema, generated by `drizzle-kit generate` from
`src/db/schema/` (`drizzle.config.ts`: `out: './drizzle'`, `strict: true`). Migrations are explicit and
replayed in order by `drizzle-orm`'s migrator on every environment; `drizzle-kit push` is deliberately
unused so the history is reproducible on Railway.

## For AI Agents

### Working In This Directory

- **Never hand-edit `meta/` and never edit an applied migration.** Production applies `.sql` files once;
  changing one afterwards desynchronises environments silently. Fix forward with a new migration.
- The journal's `when` values are ascending (`0004`: `…242101`, `0005`: `…242102`). Drizzle's migrator
  applies only entries newer than the last applied one, so a hand-added or reordered entry with a
  smaller `when` would be skipped without an error.
- Schema changes follow the workflow in `src/db/schema/AGENTS.md`: edit schema, `npm run db:generate`,
  review the SQL, `npm run db:migrate`, commit SQL + snapshot + journal together.
- A new migration must be backwards-compatible with the code that is still serving while it runs; the
  pre-deploy step runs before the new release replaces the old one.
- Statement separators are `--> statement-breakpoint`; keep them if you append hand-written statements
  to a *new* file.

### How migrations run

- **Railway pre-deploy:** `.railway/railway.ts` sets `preDeploy: 'npm run db:migrate'` →
  `src/db/migrate.ts` (single connection to `DATABASE_URL`, `migrationsFolder: './drizzle'`). A failing
  migration blocks the release. The web service runs 1 replica; the worker (`lugar-worker` in `.railway/railway.ts`)
  has no pre-deploy and never migrates.
- **Before the build:** npm `prebuild` runs `scripts/migrate-for-build.ts`. `next build` prerenders and
  queries the real database *before* pre-deploy, so a commit that adds a column and a query using it
  failed the build (`column documents.archived_at does not exist`). The script applies the same
  migrations to `DATABASE_URL_BUILD` and is a no-op when that variable is unset (local builds and the
  E2E build never touch a database). Failure aborts the build. After it, the pre-deploy migrate is an
  idempotent no-op.
- **Tests:** `tests/helpers/db.ts#migrateTestDatabase` creates `lugar_test` if missing and applies this
  folder; integration tests therefore also verify that the whole chain replays on an empty database.

### Testing Requirements

- After adding a migration run `npm test` with Postgres up (`npm run docker:up`); the integration suites
  (`tests/integration/schema-invariants.test.ts`, `outbox.test.ts`, `publishing.test.ts`) migrate a
  clean database from `0000` and will fail if the chain does not replay.
- Local application: `npm run db:migrate`. There is no `db:reset` script.

### Common Patterns

- Index names are explicit and suffixed (`_uq`, `_idx`) in the schema, so SQL diffs read cleanly.
- Partial indexes show up as `WHERE …` clauses in generated SQL (`0004`).
- Data migrations are plain SQL with an explanatory comment header (`0005`).
