# Чек-лист запуска

Что должно быть правдой до того, как сайт станет публичным. Разделено по тому, кто это делает и что
блокирует запуск, а что нет.

Обзорный экран `/admin` показывает часть этих пунктов цифрами — начните с него.

---

## Блокирует запуск

### Данные владельца

Ни одного выдуманного факта в системе нет. Пока поле не заполнено, соответствующий элемент на сайте
**не показывается** — не «показывается пустым», а отсутствует. Проверьте раздел «Настройки»,
незаполненные помечены.

- [ ] Телефон в формате для показа и в формате E.164
- [ ] Номер для WhatsApp (цифрами, без плюса)
- [ ] Публичный email
- [ ] География работ или физический адрес — **только если он должен быть публичным**
- [ ] Юридическое наименование и NIF/CIF
- [ ] Реальные ссылки на Instagram и Facebook
- [ ] «Картинка для соцсетей» — показывается при отправке ссылки в мессенджер, лучше 1200×630
- [ ] Логотип

Логотипы EGGER / BLUM / HETTICH — **только с письменного разрешения правообладателя**. Без него
бренды остаются текстом. Это безопаснее и выглядит намеренно.

### Изображения

- [ ] Счётчик заглушек на обзорном экране равен нулю
- [ ] У каждого изображения заполнен alt-текст
- [ ] Фотографии проектов портфолио — настоящие работы студии, с правом на публикацию

Заглушка с надписью «ЗАМЕНИТЬ» на публичной странице — это то, что увидит клиент.

### Юридические страницы

Черновики политики конфиденциальности и политики cookie написаны под GDPR и LOPDGDD и описывают
именно этот сайт: те поля, которые собирает форма, те cookie, которые он ставит, и тех обработчиков,
которые действительно получают данные. Это черновики для юриста, а не юридическая консультация.

- [ ] В тексте заменены плейсхолдеры: `[ЮРИДИЧЕСКОЕ НАИМЕНОВАНИЕ]`, `[NIF/CIF]`,
      `[ЮРИДИЧЕСКИЙ АДРЕС]`, `[EMAIL ДЛЯ ЗАПРОСОВ]`
- [ ] Подтверждены сроки хранения (в тексте они в квадратных скобках — это предложение студии,
      а не требование закона)
- [ ] Юрист прочитал оба текста
- [ ] Тексты опубликованы на всех трёх языках
- [ ] Плашка «Это шаблон» снята — `showTemplateNotice: false` в сиде и через `legal:apply`

Порядок работы с текстом. Он живёт в `src/content/legal.ts`, потому что блок юридического текста
нельзя редактировать в панели — там у него нет полей. Чтобы правка доехала до работающего сайта:

```
npm run legal:apply             # показать, что изменится
npm run legal:apply -- --write  # записать в черновик
```

Скрипт обновляет **черновик** и ничего не публикует: открыть, прочитать и опубликовать — отдельное
человеческое действие, ссылка предпросмотра в панели работает и для неопубликованных языков.

### Тексты

- [ ] Испанские тексты вычитаны носителем
- [ ] Английские тексты вычитаны носителем

Испанский — основной рынок. Тексты в системе написаны человеком, но не носителем.

### Порядок первого развёртывания

Важно: **данные заполняются на сервере, а не локально.** База на вашей машине никуда не поедет, а
загрузка фотографий без настроенного хранилища вообще откажет — намеренно, чтобы файлы не писались
на диск контейнера, который Railway стирает при каждом деплое.

**Где хранить фотографии — два рабочих варианта.**

*Volume в Railway* (без второго поставщика и без отдельной карты). Диск монтируется к сервису,
`STORAGE_DRIVER=local`, `STORAGE_LOCAL_ROOT` указывает на точку монтирования. Цена: сервис
навсегда в одной реплике, каждый деплой роняет сайт на несколько секунд (Railway намеренно не даёт
двум процессам писать в один диск), фотографии раздаёт само приложение без CDN, а объём ограничен
тарифом.

*Объектное хранилище S3* (Cloudflare R2, Backblaze B2, любое совместимое). Цена: отдельный аккаунт.
Взамен — CDN, деплой без простоя и никакой привязки к одной реплике.

Начать можно с любого: хранилище спрятано за одним интерфейсом, переключение — смена переменных,
перенос файлов — одно копирование каталога в бакет.

0. Проверить конфигурацию до деплоя:

   ```
   npm run preflight -- --production
   ```

   Скрипт читает те переменные, что у него под рукой, и проверяет **то, что ломается уже после
   сборки**: доступность базы, применённые миграции и реальную запись с чтением в хранилище.

   Для S3 он вдобавок забирает записанный файл по публичному адресу — так же, как это сделает
   посетитель. Четыре заполненные переменные доказывают только, что кто-то что-то вписал; отказывает
   обычно **публичный доступ у бакета**, который включается отдельно от токена, и тогда загрузка
   проходит, а на сайте битые картинки.

   Для Volume он проверяет, что `STORAGE_LOCAL_ROOT` — абсолютный путь и что в него можно писать.
   Незаданный путь — ошибка: файлы окажутся внутри сборки и исчезнут при следующем деплое.

   Ошибки означают «деплоить рано» и возвращают ненулевой код. Пункты «ЖДЁТ» — то, что нужно от
   владельца: без них сайт работает.

1. Подготовить хранилище — по выбранному варианту:

   *Volume*: в Railway у сервиса сайта → **Data** → добавить Volume, точка монтирования, например
   `/data/media`. Затем `STORAGE_DRIVER=local` и `STORAGE_LOCAL_ROOT=/data/media`.
   Резервные копии тома настраиваются там же — на диске лежат все фотографии студии.

   *S3*: создать бакет, выдать токен с правами на чтение и запись, **включить публичный доступ**
   и заполнить `S3_*` вместе с `NEXT_PUBLIC_MEDIA_BASE_URL`.

2. Создать в Railway проект: Postgres и сервис из этого репозитория. Конфигурация сервиса берётся
   из `railway.json` — там же миграции как pre-deploy и запуск standalone-сервера.
3. Задать переменные окружения (список ниже).
4. Задеплоить. Миграции применятся сами перед стартом.
5. Один раз выполнить `npm run db:seed` — создаст страницы, настройки и этапы воронки.
6. Один раз выполнить `npm run auth:bootstrap` — создаст владельца.
7. Создать **второй сервис** из того же репозитория для отправщика WhatsApp: в его настройках указать
   путь к конфигурации `railway.worker.json`. Без него сообщения будут копиться в очереди.
8. Войти в `/admin` и заполнить данные и фотографии.

**Регион — Амстердам, и это не вкус.** В `railway.json` стоит `europe-west4-drams3a`: база хранит
имена, телефоны и переписку клиентов из Испании, а по умолчанию Railway разворачивает сервисы в США.
Единственный европейский регион у Railway сейчас этот. Том следует за регионом своего сервиса, так
что фотографии окажутся там же. Менять после запуска — только через миграцию базы.

**Смена домена требует правки двух переменных.** `NEXT_PUBLIC_APP_URL` вшивается в сборку и задаёт
канонические ссылки, hreflang и sitemap; `BETTER_AUTH_URL` — возврат после входа в панель. Railway
меняет адрес молча, и сайт продолжает объявлять старый: страницы открываются, а каждая каноническая
ссылка и весь sitemap указывают на хост, которого больше нет. Снаружи это незаметно — по canonical
ходит поисковик, а не человек. После смены адреса обязательно пересоберите: значение попадает в
сборку, а не читается в работе.

**Проверки — в GitHub Actions, выкладка — за Railway.** Railway связан с репозиторием и разворачивает
`main` сам; workflow, который тоже вызывал бы `railway up`, дал бы два развёртывания на пуш, а с
подключённым томом они не могут идти одновременно. Поэтому `.github/workflows/checks.yml` только
проверяет — линтер, типы, форматирование, юнит-тесты.

Чтобы это было заслоном, а не отчётом задним числом, включите **Wait for CI** в Railway → сервис →
Settings. Без него Railway начинает сборку сразу после пуша и результат проверок не смотрит.

Если привязка репозитория к Railway не устанавливается (окно авторизации закрывается, CLI отвечает
`Unauthorized`), причины обычно такие: у аккаунта Railway не привязан GitHub — при регистрации по
почте связи нет, её создают в настройках аккаунта; приложение Railway установлено на другой аккаунт
GitHub или не имеет доступа именно к этому репозиторию; браузер блокирует возврат из окна.

**Держите одну реплику.** Кеш у Next по умолчанию по-инстансный: при двух репликах публикация на
одной оставит вторую отдавать старую страницу. Выглядит это как «панель сломалась». В `railway.json`
стоит `numReplicas: 1` — не увеличивайте, пока не появится общий кеш.

**Не меняйте `HOSTNAME` на `127.0.0.1`.** Standalone-сервер, привязанный к конкретному адресу вместо
`0.0.0.0`, отвечает на внутренний rewrite абсолютной ссылкой на `localhost`, и главная страница
уходит в бесконечный редирект. Тесты запускают сервер с тем же `0.0.0.0`, что и боевой конфиг, —
именно чтобы такое ловилось здесь, а не на домене.

### Инфраструктура

- [ ] Домен привязан, https работает
- [ ] `NEXT_PUBLIC_APP_URL` — боевой домен без слэша на конце
- [ ] `BETTER_AUTH_SECRET` и `PREVIEW_SECRET` — длинные случайные строки, **не те, что в разработке**
- [ ] Объектное хранилище настроено: `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`,
      `S3_SECRET_ACCESS_KEY`, `NEXT_PUBLIC_MEDIA_BASE_URL`
- [ ] `STORAGE_DRIVER` соответствует выбранному варианту хранения

  Это единственный пункт, у которого нет одного правильного значения, и раньше он противоречил
  разделу выше. С объектным хранилищем (R2) переменная не ставится вовсе. С Volume она равна
  `local`, а `STORAGE_LOCAL_ROOT` указывает на точку монтирования — **и только на неё**: без
  смонтированного диска `local` означает, что Railway сотрёт все фотографии при следующем деплое.
  Сегодня работает второй вариант.
- [ ] Миграции применены на боевой базе
- [ ] Проверено, какой заголовок на боевом домене содержит настоящий адрес посетителя

  Ответы самой Railway на этот вопрос противоречат друг другу: в одном месте сказано, что край
  **перезаписывает** `X-Forwarded-For` (тогда верен первый адрес в списке), в другом — что
  **дописывает** свой в конец (тогда первый адрес выбирает отправитель запроса). Код предпочитает
  `X-Real-Ip`, который прокси перезаписывает, и падает обратно на первый `X-Forwarded-For`.
  Пока это не проверено на живом домене, к адресам в журнале изменений нужно относиться как к
  «что заявил запрос», а лимит заявок «5 в час с адреса» обходится подделкой заголовка —
  ограничение по номеру телефона при этом продолжает работать.
- [ ] Первый владелец создан командой `npm run auth:bootstrap`

  Скрипт отказывается работать, если владелец уже существует, поэтому второго администратора им не
  создать. Переменную `INITIAL_OWNER_EMAIL` после запуска можно убрать — резервное письмо о заявке
  (ниже) на неё больше не завязано, оно уходит на «Публичный email» из настроек.
- [ ] Резервное копирование базы включено, снапшоты тома тоже — и восстановление хоть раз
      проверено на копии. Процедура и что именно сверять: `docs/backup-restore.md`
- [ ] `WHATSAPP_INTERNAL_RECIPIENTS` задан — **даже в режиме `fallback`, до верификации Meta**

  Строка в очереди уведомлений создаётся, только если есть кому её адресовать. Без этой переменной
  очередь пуста при любой заявке, и резервному письму (следующий пункт) неоткуда взяться — не
  потому что оно не настроено, а потому что уведомлять было решено пока некого. Значение — номер
  владельца в формате `+34...`; шаблон (`WHATSAPP_LEAD_ALERT_TEMPLATE_NAME`) можно оставить пустым
  до одобрения Meta, он получает рабочее значение по умолчанию.
- [ ] `RESEND_API_KEY`, `EMAIL_FROM` и «Публичный email» в настройках заданы — это единственный канал,
  по которому заявка доходит, пока WhatsApp не подключён или недоступен

## Не блокирует, но проверьте

### Почта

`RESEND_API_KEY` и `EMAIL_FROM` теперь в блокирующем списке выше — без них резервное уведомление о
заявке некому уходить. Здесь остаётся только то, что этих двух переменных не требует:

- [ ] Домен отправителя у Resend верифицирован (иначе письма уходят в спам или отклоняются)

Без почты приглашения всё равно работают — ссылка показывается для передачи вручную.

### WhatsApp

См. `whatsapp-setup.md`. Сайт работает без интеграции: заявки собираются, кнопки ведут на `wa.me`,
а `WHATSAPP_INTERNAL_RECIPIENTS` из блокирующего списка выше уже направляет уведомление в почту.

- [ ] Верификация бизнеса у Meta пройдена
- [ ] Webhook подключён и проходит проверку
- [ ] Шаблон уведомления о заявке одобрен, а `WHATSAPP_LEAD_ALERT_TEMPLATE_NAME` указывает на него
- [ ] Сервис-воркер запущен в Railway
- [ ] Проверено вживую: входящее сообщение появляется в карточке

### Аналитика

- [ ] `NEXT_PUBLIC_GA_MEASUREMENT_ID` / `NEXT_PUBLIC_META_PIXEL_ID` заданы, если аналитика нужна
- [ ] Переключатель «Включить аналитику» в настройках включён

Теги не срабатывают, пока посетитель не даст согласие, — независимо от этих настроек. Порядок такой:
согласие даёт посетитель, переключатель включает владелец, и только тогда скрипт вообще загружается.

Обе переменные вшиваются в сборку, поэтому после их добавления нужен **пересбор** — иначе значения
не появятся в браузере. Это же верно для смены домена.

## Проверено автоматически

Эти утверждения покрыты тестами и проверяются на каждой сборке. Отдельно проверять руками не нужно;
если что-то из этого сломается, сборка не пройдёт.

| Область | Что доказано |
| --- | --- |
| Доступ | Аноним не читает данные админки; редактор отбивается от заявок и настроек **сервером**, а не скрытым пунктом меню |
| CMS | Черновик не виден публично; публикация меняет сайт; откат возвращает прошлую версию; невалидный блок не сохраняется |
| Фотографии | Занятое опубликованной страницей изображение не удаляется; точка фокуса переживает сохранение |
| Заявки | Отправка формы = ровно одна заявка; UTM доезжают; спам отбивается; выгрузка обезвреживает формулы Excel |
| Переадресация | Смена адреса сохраняет старую ссылку; кольцо отклоняется; живая страница выигрывает у старого правила |
| WhatsApp | Неверная подпись → 403; подпись по пересобранному JSON отвергается; дубль события идемпотентен; три воркера на 30 задач берут каждую ровно раз |
| Окно 24 ч | Закрывается за пять минут до срока; неизвестный номер считается закрытым |
| SEO | У опубликованного маршрута есть canonical и hreflang; черновики и админка в sitemap не попадают |
| Доступность | Публичные страницы и все **списочные** экраны админки (14 адресов) проходят axe по WCAG 2.1 A/AA; страницы редактирования конкретной записи — нет, для них нужна созданная запись; баннер cookie отклоняется с клавиатуры не сложнее, чем принимается |
| Скорость | Бюджет по весу страницы держится (сегодня ~400 КБ, из них 208 КБ JS); CLS ровно 0; на критическом пути нет запросов к чужим доменам |

## Чего в системе нет намеренно

Проверьте, что это совпадает с ожиданиями, до запуска, а не после.

- **Магазина, корзины, оплаты.** Сайт ведёт к разговору, а не к покупке.
- **Регистрации посетителей.** Личных кабинетов нет.
- **Автоматического объединения дублей.** Повторное обращение помечается, решает человек.
- **Гарантии однократной доставки в WhatsApp.** См. `whatsapp-setup.md`.
- **Произвольного HTML в контенте.** Блоки типизированы, вёрстку из редактора сломать нельзя.

## Что ещё не сделано

Честный список на момент написания. Ничто из этого не мешает публичному запуску, но и не появится
само.

- Раздел «Проекты»: таблица есть, экрана нет. Проекты видны в карточке клиента, но завести проект
  из панели пока нельзя — до первой выигранной сделки это ничего не блокирует.
- Замеры на реальных сетях и устройствах: вес страницы и CLS закреплены бюджетом (см. таблицу
  выше), но всё измерено на локальной машине по localhost. Как сайт открывается с мобильного
  интернета в Испании — не проверено; это делается на боевом домене после запуска.
- Вес изображений: сейчас на страницах стоят заглушки, настоящих фотографий нет. Именно они
  обычно и определяют скорость — бюджет придётся пересмотреть после загрузки реальных фото.
- Проверка живым скринридером: автоматика ловит контраст, имена и роли, но не то, как экран
  звучит целиком. NVDA или VoiceOver по ключевым сценариям — отдельная задача для человека.
- Шаблоны с подстановками при закрытом окне 24 ч: выбрать можно только шаблон без переменных.
- Создание новых страниц: набор из десяти страниц сайта задаётся при установке. Проекты в «Наших
  работах» владелец создаёт и убирает сам, а новая страница — например, ещё одно направление —
  пока задача разработчика: нужно решить, из каких блоков она собирается и куда ведёт из меню.
