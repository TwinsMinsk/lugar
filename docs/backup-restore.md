# Резервное копирование и восстановление

Две вещи, потеря которых необратима: **база данных** (заявки, клиенты, переписка, согласия, весь
контент сайта) и **том с фотографиями**. Всё остальное — код, конфигурация, схема — лежит в
репозитории и восстанавливается деплоем.

Бэкап, который ни разу не восстанавливали, — не бэкап. 29.10.2026 дамп рабочей базы восстановлен
командой из пункта 4 и совпал с ней полностью: 36 таблиц по числу строк и содержимому, 115 индексов,
324 ограничения, 7 миграций.

---

## 1. Что включено в Railway

Бэкапы включены 28.10.2026 у обоих томов — **`postgres-volume`** (база) и **`lugar-web-volume`**
(оригиналы фотографий): ежедневные хранятся 6 дней, еженедельные — 27, ежемесячные — 89. Найти их:
Railway → сервис → вкладка **Backups**. Там же снимки, которые Railway делает сам перед изменением
размера тома, и ручной снимок «Before launch 2026-10-28» без срока хранения.

Том хранит оригиналы фотографий, база на них только ссылается: потеря тома означает сайт со
ссылками в никуда, который база не починит.

Снимок тома Railway восстанавливает **только поверх того же тома** — то есть поверх рабочей базы
или фотографий. Это инструмент на случай аварии, не для проверки. Проверяют дамп (пункт 4).

Пока фотографии лежат на томе, эти два бэкапа нужно снимать **вместе**: восстановленная база и том
из другого дня расходятся по ссылкам. После перехода на объектное хранилище (R2) эта связь
исчезает — там версионирование делает провайдер.

## 2. Снять дамп руками

Перед рискованной операцией (миграция, массовое редактирование, обновление зависимостей) снимайте
дамп сами, не полагаясь на расписание.

```bash
# DATABASE_URL — публичная строка подключения из Railway
pg_dump "$DATABASE_URL" -Fc -f lugar-$(date +%Y-%m-%d).dump
```

Формат `-Fc` (custom) выбран не случайно: он сжат, из него можно восстановить отдельную таблицу и он
не зависит от версии psql так сильно, как обычный SQL-текст.

Дамп содержит имена, телефоны и переписку с клиентами. Это персональные данные: храните файл там же,
где вы храните договоры, а не в загрузках браузера, и удаляйте, когда он больше не нужен.

---

## 3. Восстановить

**Сначала в копию, а не поверх рабочей базы.** Восстановление поверх живой базы — это второй сбой
после первого.

```bash
createdb lugar_restore_check
pg_restore -d lugar_restore_check --no-owner lugar-2026-09-09.dump
```

Затем сверьте, что восстановилось то, что ожидалось:

```sql
select
  (select count(*) from documents)   as documents,
  (select count(*) from leads)       as leads,
  (select count(*) from contacts)    as contacts,
  (select count(*) from drizzle.__drizzle_migrations) as migrations;
```

Число миграций должно совпадать с числом файлов в `drizzle/` — это же сравнение делает
`/api/health`, и расхождение означает, что копия старше кода.

Если проверка сошлась и нужно вернуть базу в работу:

1. Остановите сервис сайта в Railway, чтобы никто не писал в базу во время восстановления.
2. Восстановите в боевую базу тем же `pg_restore`.
3. Запустите сервис и откройте `/api/health` — он должен ответить `status: ok`.

## 4. Проверка восстановления, не вынося данные из Railway

```bash
npm run db:restore-check
```

Команда создаёт в проекте временный сервис `restore-check` (Postgres 18, регион ЕС). Он снимает дамп
рабочей базы по внутренней сети Railway, восстанавливает его в отдельную базу внутри своего
контейнера и сравнивает с рабочей каждую таблицу — число строк и хеш содержимого, — а также число
индексов и ограничений. Затем сервис удаляется, даже если проверка не прошла. Дамп существует только
внутри контейнера; в вывод попадают названия таблиц, счётчики и хеши, но не сами записи.

Нужно: Railway CLI, вход в аккаунт (`railway login`) и папка проекта, связанная с проектом
(`railway link`). Занимает около минуты и стоит центы.

Последняя строка вывода — `Restore check passed.`; иначе команда завершается с ошибкой и показывает
лог проверки. Если запуск прервали и сервис `restore-check` остался в Railway, удалите его вручную —
команда откажется стартовать, пока он есть.

---

## 5. Что проверять раз в квартал

- [ ] последний автоматический бэкап обоих томов не старше суток (пункт 1);
- [ ] `npm run db:restore-check` проходит (пункт 4);
- [ ] снимок тома с фотографиями сделан примерно в то же время, что и бэкап базы.

Достаточно получаса раз в три месяца. Единственное, что нельзя восстановить, — это бэкап, о котором
выяснилось, что он не работает, в тот день, когда он понадобился.
